# 性能：先定位成本，再选择复杂度

仅在用户要求优化、出现实测卡顿/内存增长，或功能规模有明确预算时使用。没有证据不把普通功能变为对象池、ECS、线程或 GDExtension 重写。

## 建立可比较基线

固定目标设备、renderer、分辨率、构建类型、场景、输入/seed、实体数量和采样区间。以帧时间和卡顿分布为主，FPS 为辅；60 FPS 的帧预算约 16.67 ms，但目标帧率由项目决定。记录加载峰值和稳定状态，区分首次导入/预热与正常游玩。

通过 Profiler 的 self/total time 与调用次数、Monitors 的节点/对象/内存/绘制/物理数据定位。渲染受限要在真实图形环境测；headless 数字不能代表 GPU 性能。若暂时没有测量能力，只报告假设和需要的观测，不声称优化有效。

## 成本对应措施

| 发现的成本 | 可选择的措施与验证 |
| --- | --- |
| 不必要的每帧工作 | 缓存稳定引用、按事件更新、闲置时停 process；连续输入/模拟仍可每帧执行 |
| 大量实例化/释放峰值 | 预加载、分批生成；只有收益明确时池化，并测试 reset、信号解绑、取消旧异步和释放 |
| 绘制/透明 overdraw 或材质切换 | 降低不可见工作、适合的图集/批处理/MultiMesh；检查排序、透明和交互是否变化 |
| 物理/导航成本 | 简化碰撞、调整检测层/更新频率、减少不必要避让；保持交互正确性 |
| 加载阻塞 | 资源预算与按需后台加载，检查取结果时再次阻塞和峰值内存 |
| 重入后资源持续增长 | 分清缓存暖机与泄漏；追踪孤儿节点、常驻引用、循环引用、信号、Tween/音频 |
| 确认的纯计算热点 | 先改善算法/数据，再评估线程或原生扩展的维护、平台和边界成本 |

SceneTree 的活跃节点操作通常不线程安全；后台线程只处理合适的数据/已核验 API，结果回主线程应用。不要把“资源加载可线程化”等同于任意改节点或共享 Resource。

不用“超过 N 节点”“每帧调用 N 次”“draw calls 超过固定数量”作为通用换语言/架构门槛。每项优化复测同一情境的时间、内存和行为；没有可重复改善则保留清晰实现或撤回无收益的复杂化。
