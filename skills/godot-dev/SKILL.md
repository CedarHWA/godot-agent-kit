# Godot 需求开发

通常由用户级 `godot-project-init` 在目标项目生成本技能，与该项目规则一起维护；单独安装、用户级安装及其他已有布局同样受支持。以本次项目的 AGENTS.md、需求和实际代码为准，不因技能的安装范围而重跑初始化或改写其他项目、用户级技能。

## 执行范围

收到实现请求就持续完成本次范围的功能、正式资源、验证和清理。先读项目及上级 AGENTS.md、本次任务书、docs/requirements.md、docs/architecture.md、相关场景/资源/代码和已有改动。保留用户及其他任务的工作；普通开发不重跑初始化、重建 ComfyUI 实例或迁移引擎。用户只要求设计、评审或指定阶段时遵守该范围。

把需求变成可观察的“触发 → 结果”，包含相关失败路径。优先本次明确要求、项目约定、容易修改的合理默认值；已有信息不重复询问。大任务分成可运行的小步并完成全部授权范围，不自行缩为演示版。玩法不明确时只询问影响范围且不能推断的选择，继续独立工作。没有需求不预建通用系统。

## 未经初始化的项目

本技能可独立使用。docs/requirements.md、architecture.md、development.md 或 editor-contract.json 不存在时，以当前需求、现有场景与项目规则为准；仅补充本次任务需要的说明，不强制先运行初始化器。不确定 API 时查项目匹配版本的官方文档；没有离线库就查官网。没有 tools/check.ps1 时，复用现有检查入口，或用匹配版本 Godot CLI 执行导入、解析、所选行为测试和实际运行；不要虚构检查脚本。素材服务可用 MCP、项目 CLI 或现有流程，不依赖 Codex 专属工具名。Codex 用 $godot-dev，Harness 用 /godot-dev；两者按实际目录发现完整技能资源。

## 先用 Godot 组成游戏，再补行为脚本

新增完整玩法、页面、角色或重构功能时，先读 [场景与资源](references/scene-and-resource-design.md) 及项目约定。在已有架构记录中用简短树/表说明“功能 → 场景/内置节点 → 配置资源 → 状态所有者 → 方法/信号 → 编辑入口”，再实现一个可运行切片。先落地主要 `.tscn`、资源引用和内置能力，再补脚本行为；不要先写集中控制脚本，最后补场景壳。小修直接沿用已有边界，无需重做架构。

- 固定物件和控件保存到可编辑 `.tscn`；动态数量实例化完整 `PackedScene`。编辑器中可预览和修改的正式内容不能只存在于 `_ready()` 生成器中。
- 场景内也要有职责边界：棋盘、独立面板、角色能力等按编辑、替换或生命周期需要组合；只用一次也可能值得拆场景。父级协调流程，组件管理自身输入、表现和内部节点，不能把一个大脚本机械拆成仍由父级逐项控制的空组件。
- 节点负责需要场景树的行为；类型化 Resource / 导出属性负责设计配置；纯规则可用 RefCounted。共享配置与每个实例的状态分开。
- 组件拥有内部节点。父级注入依赖并连接事件，命令/查询使用明确方法；不要跨场景穿透内部路径或默认建立全局事件总线。
- 写自绘、手动布局、按键分支、计时或播放系统前，对照专题中的内置能力表选择载体。Theme、素材、数值、InputMap 和固定动画保留有效编辑入口；脚本不得用常量覆盖承诺可调的值。合理的浅层继承、内部 `$Path`、动态 Tween、过程生成和纯计算正常使用；自定义方案说明需求与编辑方式，不按行数、节点数或 `.new()` 数量裁决架构。
- 目录默认采用“按类型＋功能子目录”：scenes/<功能>/ 放 .tscn，scripts/<功能>/ 放 .gd，resources/<用途或功能>/ 放 .tres 等配置，assets/<媒体类型>/<用途或功能>/ 放图片、音频等素材；场景与行为脚本尽量同名、同功能相对路径，Resource 类脚本仍放 scripts。按实际内容建目录，复用有实际需求才抽公共模块。此目录偏好不改变场景和资源优先规范；已有项目保留已约定结构，只有明确要求才迁移。

## 完成前的验证

存在 `tools/check.ps1` 时执行它，否则按上面的独立项目检查路径执行；本机标准 Windows 便携引擎使用 `-IsolateEditor`，支持 `-ReportDir` 时写入本轮 `work/dev-<任务标识>/checks`。参数以实际脚本为准。实现任务还应读“调试与测试”，根据风险选择行为测试，失败后修复并复测受影响部分。

涉及可编辑内容时维护 `docs/editor-contract.json`，执行真实加载检查。审阅每个新增/明显改变的主要组件的编辑入口和实际消费者；不能用标题页一项可编辑属性代替整个游戏的可维护性。按风险在临时副本上验证布局、素材或参数不改 GDScript 即可保存、重载并改变运行结果，尤其检查 `_ready`、布局刷新及动画是否覆盖所改值；完整页面/功能覆盖这三类编辑，纯规则修复不制造无关 UI 测试。涉及共享状态时验证两实例隔离。结构检查只证明声明的节点/属性存在，不证明可编辑性和全部架构。

图形、真实输入、音频听感分别验收；技术检测、headless、文件存在、生成成功不能互相代替。不能完成的项记录实际阻碍、恢复入口和未验证状态，继续其他可独立完成的工作。用户要求正式素材时不能用空白图、静音或程序音冒充。

按“交付”保存紧凑报告及必要证据，更新重要架构/需求和具体编辑路径，清理本轮失去用途的文件。只在本次要求与相应检查全部满足时称全部完成；未验证项如实说明。用户未要求打包时不把导出当作普通开发的固定收尾步骤。

本技能的来源审阅及取舍见 [社区研究](references/community-review.md)；仅维护技能或追溯依据时读取，不作为每轮开发的必读内容。
